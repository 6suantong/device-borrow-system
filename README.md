## 一、项目是做什么的

实验室设备（开发板、传感器、工具、相机等）目前靠 **QQ 群口头申请 + Excel 人工登记**，
存在设备状态不一致、重复批准、借还无凭证、超期无人管等问题。本项目交付的是一套
**系统分析报告 + 设计级代码包**，覆盖：

- 成员查设备、提交申请、共同使用人登记、撤回申请；
- 管理员 / 负责人两级审批（重要设备需两级、普通设备一级）；
- 批准即预留、48 小时领取时限、领取 / 归还 / 异常归还转维修；
- 全程状态留痕、审批回避、结构化拒绝原因；
- 基于真实试运行日志（529 条业务事件）的问题证据链与改进方案；
- 部署形态、每日备份、每日状态对账与发布回退预案。

> 说明：按考核要求，本仓库为**设计级交付物**（数据库 Schema + Python 领域模型 +
> API 契约 + 分析与运维脚本），不是一个需要启动服务器的完整 Web 应用。

## 二、四轮迭代速览

| 版本 | 主要输入 | 核心决策与产出 |
|------|----------|----------------|
| **V1** | 原始需求材料 | 确立三大支柱：设备状态机唯一可信、占用唯一性（核心不变量）、全程留痕；设备分两级、流程分轻重；BR-01~BR-08 业务规则 |
| **V2** | 周会记录 / 访谈 / 管理员笔记 / 群内约定 | 从"流程管控"升级为"责任与透明"：审批带理由与回避、结构化拒绝原因、共同使用人、48h 领取时限、模糊约定正式化（BR-09~BR-11） |
| **V3** | 529 条业务事件 / 236 条状态转换 / 549 条访问日志 / 25 条用户反馈 | 证据驱动改进：EV-01~06 六条证据链，IMP-1~6 六项改进（占用事务化、异常归还闭环、超期治理、时限自动执行、提交幂等、列表索引优化） |
| **V4** | 部署与运维约束 | 工程闭环：容器化、每日在线备份、每日状态对账、任务告警、受控修正、版本化迁移与回归清单 |

## 五、运行方式（重点）

### 0. 最简单：直接看 Word 成品（不需要运行任何东西）

双击打开：

```
report\软件工程系统开发方向_四轮迭代分析报告_刘泽_2025181005000135.docx
```

### 1. 运行方式说明（两种任选）

**方式 A：VS Code / Trae 图形界面（推荐新手）**

1. 菜单 `文件 → 打开文件夹`，选择 `device-borrow-system`；
2. 在左侧点开要运行的 `.py` 文件；
3. 点击编辑器**右上角的 ▶ 三角形按钮**即可运行。

**方式 B：终端命令**

在 VS Code 中按 `` Ctrl + ` `` 打开终端，或打开 PowerShell，然后 `cd` 到项目目录。

### 2. 重新生成 Word 报告

```powershell
cd device-borrow-system\report
python fill_report.py --stage 4
```

参数说明：

| 参数 | 含义 | 默认值 |
|------|------|--------|
| `--stage` | 报告完成度，`1/2/3/4` 分别对应 V1~V4 | `4`（最终版） |
| `--template` | 空白模板 docx 路径 | 上级素材文件夹中的考核模板 |
| `--out` | 输出文件名 | 默认覆盖 `report` 目录下的成品文件 |

例如想单独导出一份 V2 阶段版：

```powershell
python fill_report.py --stage 2 --out 报告_V2阶段.docx
```

> 生成后终端会打印 `已生成 stage=4 -> <路径>`。

### 3. 运行领域模型自检（验证业务规则设计正确）

```powershell
cd device-borrow-system\design
python domain_model.py
```

预期输出：

```
领域模型自检通过：TC-02/03/05/06 + V2-01/02/04/06 全部符合预期
```

自检覆盖：占用唯一性拦截、非法状态流转拒绝、自批拦截、结构化拒绝原因、
48h 未领取自动释放、异常归还自动转维修等关键规则。

### 4. 复现 V3 日志分析

```powershell
cd device-borrow-system\analysis
python v3_log_analysis.py "..\..\软件工程系统开发方向\V3_运行日志材料包"
```

> 不传参数时默认分析当前目录。脚本自动按 `gb18030` 读取 GBK 编码的 CSV，
> 输出事件分布、批准失败明细、异常归还暴露窗口、超期任务记录、接口耗时分位等。
> 分析结论已整理在 [v3_analysis_result.md](analysis/v3_analysis_result.md)。

### 5. 建库与每日状态对账（V4 运维脚本）

```powershell
# 用 schema.sql 建一个 SQLite 数据库
sqlite3 lab_borrow.db < design\schema.sql        # 需要本机安装 sqlite3 命令行

# 每日对账：检查设备状态与未完结借用记录是否一致
python deploy\reconcile.py lab_borrow.db
```

退出码约定：`0` = 全部一致；`1` = 发现不一致（接入定时任务时即触发告警）；`2` = 参数错误。

### 6. 部署演练（可选，需安装 Docker）

```powershell
cd device-borrow-system\deploy
docker compose up -d
```

- `app` 容器：`restart: always` 故障自拉起，内置健康检查，端口 `8080`；
- `backup` 容器：每日 02:00 用 SQLite `.backup` 做在线备份，保留在 `backups/`。
- 详细流程见 [deploy/deploy.md](deploy/deploy.md)。

## 六、核心设计说明

### 1. 三条贯穿四轮的不变量

1. **状态唯一可信**：设备状态（可借 AVAILABLE / 预留 RESERVED / 借出 BORROWED / 维修 MAINTENANCE）
   只能通过状态机唯一写入口变更，杜绝 QQ 群与 Excel 各记一套；
2. **占用唯一性**：任何时刻一台设备最多对应一份未完结占用（条件更新原子化保证，
   解决 V3 日志中 18% 的"批准时设备已被占用"冲突）；
3. **全程留痕**：每次状态变更与审批都写日志，支持审计与受控修正（禁止直改数据库）。

### 2. 数据库（schema.sql）

8 张表：`user`、`device`、`borrow_request`、`request_co_user`（共同使用人）、
`approval_record`（审批记录）、`state_change_log`（状态变更日志）、
`event_log`（业务事件）、`notification`（通知）。

V3 针对管理端列表慢（P95 2428ms）新增 5 个索引（如
`idx_request_state_created`、`idx_event_request`）。文件末尾附有 V1→V4 版本变更记录。

### 3. 领域模型（domain_model.py）

- 用 `DEVICE_TRANSITIONS` 字典显式声明合法状态流转，`_transition()` 是唯一写入口；
- `Lab` 类提供 submit / approve / reject / withdraw / reserve_for / pickup /
  give_back / auto_release_expired / repair_done 等方法；
- 申请提交带 **10 分钟幂等窗口**，解决 V3 中 8 次重复提交导致的 504；
- 批准时做**审批人回避**与**占用条件原子更新**。

### 4. V3 六条证据链（详见 analysis/v3_analysis_result.md）

| 证据 | 数据事实 | 对应改进 |
|------|----------|----------|
| EV-01 | 批准时设备不可用失败 18 次，冲突率约 18% | IMP-1 占用条件更新原子化 |
| EV-02 | 异常归还后设备状态最长暴露 1.4 小时 | IMP-2 异常归还事务化 + 维修闭环 |
| EV-03 | 超期定时任务 2 次 500 失败且无告警 | IMP-3 每小时扫描 + 失败重试告警 |
| EV-04 | 7 份批准后滞留未领取，最长 101.9 小时 | IMP-4 48h 时限自动执行 |
| EV-05 | 8 次提交 504，用户反复点击 | IMP-5 提交幂等与超时降级 |
| EV-06 | 管理端列表 P95 2428ms | IMP-6 列表索引与查询优化 |
