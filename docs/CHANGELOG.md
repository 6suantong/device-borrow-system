# 版本变更日志（CHANGELOG）

四轮迭代均在上一版基础上做增量演化。格式：`[版本] 变更摘要`。

## V1 —— 从需求到工程意图
- 确立核心不变量：占用唯一性（一台设备任一时刻至多一个有效占用）、
  设备状态与借用记录一致、全程留痕。
- 业务规则 BR-01 ~ BR-07：四态状态机、占用唯一性、两级分类流程
  （重要设备审批 / 普通设备快速通道）、批准即预留、48h 超时释放、
  异常归还强制入维修、全程留痕。
- 数据模型：user / device / borrow_request / state_change_log / event_log，
  notification 表预留。
- 领域模型 `design/domain_model.py`：状态机唯一写入口 + 六个核心用例 +
  内置自检（TC-02/03/05/06）。
- API 契约 `design/api-contract.md` 初版。
- 报告完成 V1 章节（1.1-1.8）。

## V2 —— 需求扩展与复杂规则
- 变更识别与影响分析：对材料A-D的诉求区分需求/规则/约束/异常/非功能（报告 2.1）。
- 规则变更：BR-03 审批理由+优先级排序；BR-05 领取时限正式化（pickup_deadline
  + T-24h 提醒 + 48h 自动释放）；BR-06 异常归还升级为事务约束。
- 新增规则：BR-08 提交幂等、BR-09 审批回避、BR-10 结构化拒绝原因、
  BR-11 实际使用人登记。
- 数据模型：borrow_request 增 5 字段；新增 request_co_user、approval_record；
  notification 启用（schema.sql）。
- 领域模型：submit 幂等去重、approve 写审批记录、新增 reject/withdraw；
  自检覆盖 V2-01/02/04/06（domain_model.py）。
- API 契约：审批记录端点、优先级/使用人字段、幂等语义（api-contract.md）。
- 报告完成 V2 章节（2.1-2.6）；V1 能力回归项冻结。

## V3 —— 基于运行数据改进
- 日志分析：analysis/v3_log_analysis.py + v3_analysis_result.md

  失败、7 份滞留、8 次 504、列表 P95 2428ms）。
- 改进需求 IMP-1~IMP-6 与指标基线（冲突率<1%、即时入修 100%、检出≤1h、

- domain_model.py：repair_done 受控转换（IMP-2）、占用条件更新原子化
  示意（IMP-1）、扫描每小时（IMP-3/4）。
- api-contract.md：分页、维修完成/受控修正端点、幂等键。
- 报告完成 V3 章节（3.1-3.5），含“看起来异常但暂不改软件”的判定
  （U014 重复记录未复现、U031 感知与日志矛盾）。

## V4 —— 部署运维与优化（最终版）
- 部署形态：内网单机 Docker Compose（app + 备份任务），SQLite WAL；
  取舍依据：负载极低，单体+嵌入式调度最简可靠（FDE 式决策）。
- 数据可靠：每日 02:00 在线备份+NAS 异地副本+每月恢复演练；发布前强制备份。
- 故障恢复：restart=always + /healthz；恢复后运行 reconcile.py 对账，
  不一致项经受控修正入口处理。
- 发布/回退：镜像 tag 化；核心回归全绿才可发布；回退=切回上一 tag+恢复备份。
- 报告完成 V4 章节（4.1-4.5）、四轮演化总表与最终反思；报告定稿
  （stage=4 全量生成）。
- 四个 FDE 闭环案例：真实超期任务问题（承接 V3 EV-03）+ 三个模拟现场
  问题（locked 写冲突/人工改库/容量信号），均以运行观测证据评估决策。
