## 二、证据链（与报告 3.1 对应）

### EV-01 批准冲突（P0）——占用校验非原子
- 业务事件日志：18 条 `APPROVAL_FAILED_DEVICE_UNAVAILABLE`，detail 均为
  "device state changed after submission"，占批准尝试 18%。
- 设备状态日志：18 条 `MANUAL_SYNC` note="state updated by another borrowing
  record"，与失败次数一一对应（人工善后证据）。
- 典型链：R0007/BOARD06 —— 9/1 提交 → 9/2 09:27 被另一借用记录同步占用 →
  9/2 09:51 批准失败。
- 反馈互证：A02（9/9 两管理员同设备）、U022（9/4 看时可用批准时不能借）。

### EV-02 异常归还暴露窗口（P0）——BR-06 未强制
- 4 次异常归还设备先回 `AVAILABLE`（note=abnormal flag recorded separately），
  0.7~1.4 小时后才由 `ADMIN_CORRECTION` 修正入 `MAINTENANCE`：
  CAM01@9/3（1.4h）、CAM02@9/4（1.3h）、CAM02@9/6（1.4h）、BOARD03@9/10（0.7h）。
- 另 5 次直接 `BORROWED→MAINTENANCE`（note=abnormal return）——处理路径不一致。
- 即时入修率 = 5/9 = 56%。
- 反馈互证：A01（9/4 11:20"备注了但列表仍可借"，正处 CAM02@9/4 窗口后）。
- 伴生证据：CAM01 9/9 02:21 `MAINTENANCE→BORROWED`（MANUAL_SYNC）——维修中
  设备被借出，维修完成无受控流程。

### EV-03 超期治理失效（P1）
- `overdue-scan` 每日仅 08:00 执行一次；9/5、9/11 两次 HTTP 500（4800ms）。
- 11 条 `OVERDUE_DETECTED` 全部 detail="no automatic user notification recorded"。
- R0001、R0076 检出时间晚于实际归还时间（扫描滞后直接证据）。
- 反馈互证：A03（9/11"有时第二天才发现"）、U040（9/14"没有提醒"）。

### EV-04 批准后滞留（P1）——BR-05 未落地
- 7 份申请批准后始终未领取未撤回：R0026/R0070/R0027/R0109/R0062/R0052/R0082。
- RESERVED 最长停留 101.9h（R0090/BOARD01）；全程无 AUTO_RELEASE 事件。
- 反馈互证：U031（9/3）、A03（9/6"不知保留还是释放"）。

### EV-05 提交链路健壮性（P2）
- `POST /api/applications` 134 次请求，8 次 HTTP 504（3.2~6.4s），126 次成功。
- U014 反馈"转圈重复点击出现两条相似记录"，但同用户同设备 10 分钟窗口
  重复提交检测为 0 组；U014 9/12 提交在日志中仅 1 条 201。
- 判定：504+无幂等设计是真实缺陷；"两条记录"未获日志支持（感知偏差）。

### EV-06 管理端列表性能（P2）
- `GET /api/admin/applications` n=42，中位 606ms、最大 2428ms；
  其余接口中位多在 150ms 内（4~10 倍差距）。
- 反馈互证：A02（9/14"刷新要等两三秒"≈最大值）。

### 其他观察（不单独立项）
- 16 次 `APPLICATION_REJECTED` detail 全空——拒绝原因未结构化（V2 BR-10
  未实现），与 U011 反馈互证。
- `BORROWED→BORROWED`、`RESERVED→RESERVED` 空转换各 3 条——MANUAL_SYNC
  噪声，随 EV-01 事务化改造消除。
- U031 反馈"设备一直被占"与其 R0054 实际按时领取的日志矛盾——用户感知
  问题，暂不改软件（报告 3.5"暂不处理"案例）。
